# 方案与取舍

模型每轮拿到用户要求和之前的工具结果，返回一个动作及参数。程序执行后，把返回值交给下一轮模型。循环中没有写死“检查失败就一定重试”的路径。

可选动作有三个：

| 动作 | 做什么 | 返回什么 |
| --- | --- | --- |
| `search` | 按产品名、关键词或别名查资料 | 产品 ID、事实 ID、原文、品牌用语表 |
| `check_script` | 接收模型安排的分镜，生成旁白并检查 | 每镜时长、引用、总时长、风险项 |
| `finish` | 完成、追问或停止 | 状态、说明、待补充项 |

模型先选事实、开场和收尾，工具再把事实 ID 转成原文。这样，口播内容可以逐句回查。每次 `check_script` 都保存一份版本；模型能看到超出了几秒、哪句触发规则，再决定删什么。

## 为什么不直接让模型报时长

模型写出的“约三十秒”不方便复核。这里按旁白中的汉字数和英文词数估算：每秒 4 个单位，每镜加 0.6 秒停顿，最低 2 秒。参数放在规则文件，修改语速就能观察结果变化。最终剪辑时再按实际配音微调。

## 完成状态怎么判断

`completed` 必须指向最新且检查通过的 `script_id`。漏填关键输入、跳过检查、使用旧版本 ID，都会把错误返回模型。执行达到 8 步时，程序返回未完成，并保留已经产生的稿件。

调用失败不会自动改成成功。工具错误会进入下一轮观察，模型自己决定重试或停止；模型接口失败则结束本次执行。

## 技术选择

使用 Python 标准库实现循环、JSON 读写和本地工具。流程不长，没有再引入 Agent 框架，动作选择和状态变化可以直接在 `src/agent.py` 中读到。

Codex CLI 只充当动作选择模型，每次用 JSON Schema 限定返回结构。本地工具由 Python 执行。另留了兼容 Chat Completions 的接入类，切换接口不需要改业务工具。

这次没有做向量库。合成资料很小，关键词与别名检索已经能测出空结果、换词补查和引用检查。资料扩大后，再比较关键词检索和向量检索的命中率。
